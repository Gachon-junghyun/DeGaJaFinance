# module_lens 설계 — 조사를 표로: 방법 찾기 → 증거 → 생각 → 결과 → 역전파

> **뭐냐:** 매일 조사(수급·기술·향방)를 마크다운 원장이 아니라 **표(SQLite)** 에 쌓고, 새 조사는 지난 물음을 **낱말 검색 + 의미(임베딩) 검색**으로 찾아 «이런 물음엔 어떤 방법·근거가 맞았나»부터 보고 시작하게 하는 하네스의 설계. DeGaJa_Agent `module_table` 과 같은 꼴을 투자 조사에 옮긴 것이다.
> **언제 읽나:** `module_lens` 의 장부 층을 지을 때(오케스트라 갈래 나누기 전), 데스크 프로토콜에 이 명령들을 붙일 때.
> **안 담는 것:** 실험 수치와 기각된 길 → [`lab/NEWS3D_20261030.md`](../lab/NEWS3D_20261030.md) · 데이터 층(가격·링크·라벨) 사용법 → [`MODULE_MAP.md`](../MODULE_MAP.md#module_lens) · 시나리오 산문 원문 → `handoff/SCENARIOS*.md`(옮기기 전 창고).

## 0. 왜 표인가

`handoff/SCENARIOS*.md` 에 이미 예상 168건과 채점 로그가 있다(FIRED-A 73 · B 78 · C 131 · EXPIRED 118). 문제는 셋이다.
1. **너무 길다.** 1.3MB 를 매 실행 통째로 읽는다(사람: *«md 로 하니까 너무 길어져»*).
2. **찾을 수가 없다.** «전에 비슷한 물음에 뭘 봤고 맞았나»를 물을 길이 없다 — 통째로 읽거나 grep 뿐이다.
3. **근거별 비중(%)이 없다.** 그래서 «무엇이 좋았나»를 모을 수 없고, 채점이 손이라 기한을 118번 놓쳤다.

`module_table` 이 같은 문제를 풀었다: 원본은 표, 문서는 표에 못 담는 긴 그림·절차만, 새 세션은 «목표 낱말»로 지난 시행착오를 찾는다. 같은 꼴로 간다.

## 1. 한 번의 조사 — 다섯 걸음

| 걸음 | 하는 일 | 명령 | 표에 남는 것 |
|---|---|---|---|
| ① 방법 찾기 | 물음을 넣으면 **닮은 지난 물음**과 거기서 **잘 맞던 방법·근거 종류**가 나온다 | `find "<물음>"` · `show Q12` | — (읽기만) |
| ② 증거 찾기 | 권장 방법으로 근거를 모은다 — 근거 하나 = 한 줄, 값·출처 링크와 함께 | `ev Q12 <방법> "<읽은 값>" --supports A --link …` | `evidence` |
| ③ 조사 | 근거가 모자라면 더 판다. 버린 방법도 적는다(`--dead`) — 다음 조사가 안 넘어진다 | `ev … --dead "<왜 못 썼나>"` | `evidence`(죽은 줄) |
| ④ 증거와 함께 생각 | 갈래·확률·판정 날짜를 정하고, **근거마다 비중 %** 를 싣는다(장부가 권장을 내민다) | `think Q12 --branch A:50 B:40 C:10 --weights e3:30,e4:25,…` | `questions` 갱신 |
| ⑤ 결과 · 역전파 | 날이 오면 자동(가격·FRED·수급) 또는 데스크가 판정. 근거·방법마다 점수가 쌓인다 | `due` · `resolve Q12 A --value …` · 밤마다 `learn` | `outcomes` |

## 2. 표 셋 — 고정, 도메인·시장이 늘어도 안 는다

**`questions` 물음** — 사건 전에 적은 «무엇이 어떻게 될지» 하나.

| 칸 | 뜻 | 예 (옛 S1) |
|---|---|---|
| `id` · `legacy` | `Q12` · 옛 시나리오 번호 | Q12 · S1 |
| `asked_at` | 적은 시각. **`settle` 보다 앞서야 갈래·확률을 받는다** | 2026-07-22T21:10+09:00 |
| `desk` · `subject` | 누가 · 종목·업종·시장·거시 열쇠 | industry_US · GOOGL |
| `title` | 물음 한 문장 — **검색 열쇠** | 알파벳 FY26 capex 가이던스가 어떻게 바뀌나 |
| `settle` · `observable` | 판정 날짜 · 무엇을 보고(기계가 읽으면 `px:`·`fred:`·`flow:`) | 2026-07-22 AMC · `text: FY capex guide` |
| `branches` | 갈래마다 조건 · 확률 % | A >$190B 50 · B 180~190 40 · C 하향 10 |
| `note` | 생각의 사연 — **길이 제한 없음**(module_table 노트 칸과 같다) | 사전 확률을 왜 그렇게 뒀나… |
| `status` | 열림 · 판정됨 · VOID · AMBIGUOUS | |

**`evidence` 근거** — 물음 하나의 근거 하나. 산 근거의 비중 합 = 100.

| 칸 | 뜻 | 예 |
|---|---|---|
| `question` · `id` | | Q12 · e4 |
| `method` | **어떻게 얻었나** — 다른 물음에도 쓰이는 일반 이름 | 추정치 30일 상·하향 수 세기 |
| `kind` · `key` | 종류(수급·추정치·옵션·거시·공시·뉴스 단어·가격) · 정규 열쇠 | 추정치 · `estimate_revision_30d` |
| `reading` | 읽은 값 | 1↑ : 4↓ |
| `supports` · `weight` | 미는 갈래 · 비중 % | C · 25 |
| `impact` | 사전 파급력(E2 표에서 자동, 없으면 1.0) | |
| `dead` | 못 쓴 방법이면 이유(비중 0) | |
| `note` · `link` | 사연(길이 제한 없음) · `module_evidence` ID·기사 `url_hash`·리포트 | |

**`outcomes` 결과** — 물음 하나의 판정.

| 칸 | 뜻 |
|---|---|
| `question` · `fired` · `value` | 일어난 갈래 · 관측값 |
| `scored_at` · `scorer` | 언제 · `auto` 또는 데스크 |
| `price_1d/3d/5d/20d` | 변동성으로 나눈 초과수익(자동, `lens.db` 가격) — «갈래는 맞았는데 가격은 반대»가 따로 보이게 |
| `brier` | 갈래 확률의 브라이어 점수(자동) |
| `note` · `link` | 판정 사연 |

**색인 둘 — 사본, 언제든 다시 짓는다**(`reindex`): `q_fts`(물음 제목·주제·근거 방법·노트의 낱말, FTS5) · `q_vec`(물음 제목 + 근거 방법의 768차원 벡터, `news_vectors.db` 와 같은 모델 `jhgan/ko-sroberta-multitask`).

## 3. 찾기 — 낱말과 의미를 같이

```
find "하이퍼스케일러 capex 가 메모리에 미치는 영향"
```

1. 낱말: `q_fts` bm25 로 후보 300개 (module_table 과 같은 이유 — 통째로 훑으면 10만 줄에서 8~10초).
2. 의미: 물음을 같은 모델로 인코딩 → `q_vec` 코사인 상위 300개. «capex» 대신 «설비투자»라 써도 잡힌다.
3. 합친 점수 = 0.5 × 낱말 + 0.5 × 의미. 상위 8개 물음을 낸다.
4. 그 물음들의 근거를 **방법별로 묶어** «이 방법으로 낸 근거가 미는 갈래가 몇 번 일어났나 · 표본 수»를 붙인다 → **① 방법 찾기의 답.**

```
비슷한 지난 물음 5건 (Q12 알파벳 capex · Q31 MSFT·META capex · …)
  잘 맞던 방법:   추정치 30일 상·하향 수 세기   7/9 맞음   ← 먼저 써라
                 옵션 내재 변동 대비 반응      5/8
  잘 틀리던 방법: 셀사이드 목표가 괴리          2/7
  🎲 방법이 하나뿐인 물음이 3건 — 다른 방법 하나를 같이 재 봐라
```

⚠ **P6**: 의미 검색은 모델을 올려야 해서 몇 초 걸린다 → 훅에서는 낱말만, `find` 를 손으로 부를 때 의미까지. 인코딩 함수는 `module_news_data._embed` 를 재사용(lazy import), 이 모듈은 `DB_READ_CMDS` 에 안 넣는다.

## 4. 결과와 역전파

| 관측값 꼴 | 판정 |
|---|---|
| `px:<티커>` · `fred:<ID>` · `flow:<…>` | **자동**, 밤마다 `score` |
| `text:` (가이던스 문장·정책 발표) | 데스크가 `resolve`. 기한 지난 물음은 **`due` 가 다음 실행 첫 화면에** 띄운다 |

판정이 들어오면 산 근거마다:

```
맞음 = +1 (그 근거가 민 갈래가 일어남) / −1 (다른 갈래) / 0 (VOID·AMBIGUOUS)
기여 = 비중/100 × 맞음
방법·열쇠의 신뢰도 = Σ기여 ÷ (Σ비중/100 + 5)          ← 표본이 적으면 0 쪽으로 줄여 잡는다
적중률 = Beta(1+맞음, 1+틀림) 평균과 80% 구간
```

④에서 장부가 내미는 권장 비중 ∝ **파급력 × 신뢰도**(한 근거 상한 40%, 표본 10개 전엔 동일비중). 데스크가 다르게 실어도 실제 비중이 남으므로, «권장보다 덧칠한 쪽이 더 맞았나»도 나중에 잴 수 있다.

## 5. 시작 재료와 옮기기

- `handoff/SCENARIOS*.md` 168건 → `questions` + `outcomes`. 산문은 `note` 칸에 통째로 넣는다(길이 제한 없음).
- 산문에 든 근거는 방법·종류·열쇠로 뽑아 `evidence` 에 넣되, **비중이 없었으므로 동일비중 + `backfilled`** 표시. 학습에서 가중을 낮춘다.
- 산문 파일은 옮긴 뒤 **창고**(지우지 않는다). 데스크는 산문 대신 `find`·`due`·`show` 를 읽는다 → 실행마다 읽는 양이 1.3MB 에서 물음 몇 개로 준다.
- `module_epistemics` 민감도 원장 9종목도 `evidence` 줄로 옮기고, `factor_confidence()` 는 lens 의 신뢰도를 읽게 바꾼다(두 벌 금지).

## 6. 원본 자리와 백업

원본은 표다(`data/lens_ledger.db` — 가격·링크 파생물 `lens.db` 와 **파일을 나눈다**: 하나는 지워도 되고 하나는 안 된다).

## 9. 지은 상태와 첫 학습 (2026-10-31)

오케스트라(Codex 7갈래)로 지었다. 장부 `data/lens_ledger.db`, 백업 `handoff/lens/*.jsonl`. 옛 시나리오 165건(정의 없는 S121·S144·S164 제외) · 근거 896줄 · 판정 142건.
백필 판정은 독립 검증 48건(불일치 후보 33 + 무작위 15) 중 46건 일치(96%), 틀린 2건(S8 → 열림, S14 → 애매)은 고쳐 넣었다.

첫 신뢰도(근거 종류별, 갈래를 민 근거만 · 백필이라 거칠다):

| 종류 | 근거 수 | 민 갈래가 일어남 | 적중률(80% 구간) |
|---|---|---|---|
| 공시·실적·가이던스 | 8 | 6 | 0.70 (0.51~0.87) |
| 거시 데이터 | 11 | 4 | 0.38 |
| 가격·상대강도 | 90 | 39 | 0.43 (0.37~0.50) |
| 뉴스 | 20 | 8 | 0.41 |
| **수급** | **32** | **5** | **0.18 (0.10~0.26)** |

- 방법 단위로 가장 나은 것: «정해 둔 지표의 과거 분포 위치를 잰다» 23번 중 17번(0.72). 가장 나쁜 것: «가중·동일가중 수급을 폭·거래량 문턱과 비교» 7번 중 0번.
- 확률 보정: 60~80% 라 한 갈래 29건은 69% 일어났다(잘 맞음). 80~100% 5건은 60% — 과신 기미(표본 작음).
- ⚠ 읽는 법: 백필 근거의 «미는 갈래»는 Codex 가 산문에서 뽑았고 비중은 동일비중이다. 수급 근거가 많이 틀린 건 «수급이 쓸모없다»가 아니라 «이 데스크가 수급을 근거로 고른 갈래가 자주 빗나갔다»이다. 새 물음이 직접 비중을 실어 쌓이면서 이 표가 바뀌어야 한다.
