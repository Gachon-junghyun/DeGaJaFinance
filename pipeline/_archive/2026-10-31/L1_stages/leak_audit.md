# L1 · LEAK_AUDIT — 끝난 런이 지불하고 걷지 않은 것 (stage)

> **사후 감사 스테이지.** 데스크는 자기가 **한 것**을 채점한다(§5 self-backtest). 이 스테이지는
> 자기가 **하지 않은 것**을 채점한다 — 버린 이름, 놓은 이름, 못 본 이름.
> 런이 끝나고 며칠 뒤(≥3 세션) 그 런을 대상으로 돌린다. 오늘 런을 오늘 감사할 수는 없다.
> Runtime: `--run {감사대상 런 날짜}`. Output: `llm_outputs/{today}/LEAK_AUDIT.md`.

## L2/L3 called
- L3 [reject_ledger](../L3_functions/reject_ledger.md) — 명시적 거부의 사후 점수
  (`scripts/reject_ledger.py score`).
- L3 [missed_ledger](../L3_functions/missed_ledger.md) — ★ **이 스테이지가 그 원장의 공급원이다.**
  `leak_scan` 은 매 감사마다 누수를 새로 계산하지만 **아무것도 적립하지 않는다** — 다음 감사가
  같은 이름을 처음부터 다시 발견한다. B/C/D 클래스를 원장 행으로 옮겨야 누적된다.
- L2 [carryover](../L2_modules/carryover.md) — 무장됐다가 아무도 다시 읽지 않은 watch 조건,
  그리고 `revives_if` 가 참이 된 행.
- 결정론 계산은 `scripts/leak_scan.py` 가 전부 한다 — 이 프롬프트는 **분류와 처방**만 한다(P4).

```bash
python -X utf8 scripts/leak_scan.py --run {대상런} --floor-jo 1.0 --top 25
python -X utf8 scripts/reject_ledger.py score
python -X utf8 scripts/missed_ledger.py score
```

## ★ 두 개의 방법론 가드 — 이걸 어기면 감사가 시스템을 정확히 반대로 고친다

### 가드 1 — 후행 채점 금지 (동어반복 함정)
상태를 **과거 수익률**로 채점하면 안 된다. OBV 는 가격방향×거래량 누적이므로 **오른 종목은
기계적으로 OBV 가 매집이다.** 실측 2026-07-23: 후행 20일로 보면 `OBV 매집 +42.2% / 분산 −24.5%`
라는 압도적 단조 사다리가 나오지만, **선행으로 보면 사라지거나 뒤집힌다.**
→ **반드시 `leak_scan` 의 선행검정 표만 쓴다**(런 시점 상태 → 그 이후 실현).

### 가드 2 — 창의 레짐을 라벨링하라 (한 창은 필터를 검증하지 못한다)
같은 필터가 창에 따라 정반대로 나온다. 실측:

| 창 | 🟢가속 | 🔴분산 | 유니버스 |
|---|---|---|---|
| 07-16 → 07-23 | **+8.18%** | — | +0.71% |
| **07-20 → 07-23 (격렬한 반등)** | +7.77% | ★ **+8.22%** | +5.08% |

**반등 창에서는 가장 얻어맞은 것이 가장 튄다.** 07-20 창만 보고 "🔴분산을 사야 한다"로 고치면
다음 하락에서 죽는다. **감사문은 창의 레짐(반등/하락/횡보)과 유니버스 평균을 먼저 적고,
결론은 최소 2개 창에서 부호가 같을 때만 낸다.**

## 누수는 네 종류이고, 처방이 서로 다르다

`leak_scan` 이 자동 분류한다. 각 클래스에 대해 **다른 질문**을 물어라.

| 클래스 | 뜻 | 물어야 할 것 |
|---|---|---|
| **A. 런에 있었음** | 잡았다 | 잡고 **왜 안 걷었나** — 거부(→원장)인가, 사이징인가, 태그가 약했나 |
| **B. 커버리지 소실** | 과거 ≥3런 다뤘는데 이 런엔 없음 | ★ **누가 추적을 놓았나.** 섹터가 로테이션에서 쉬었나? 태그가 이름이 아니라 섹터에 붙어 있었나? |
| **C. 스쳐감** | 1~2런 등장 후 사라짐 | 승격 문턱이 옳았나. 그때 무엇이 부족했고 지금은 채워졌나 |
| **D. 발굴 부재** | 한 번도 등장 없음 | ⚠ **여기서 후회하기 전에 선행검정을 보라** |

### ⚠ D(발굴 부재)를 자동으로 실패로 세지 마라 — 클래스 초과수익으로만 판정한다
**D 는 개별 이름이 아니라 *클래스 초과수익*으로 판정한다. 양수일 때만 발굴 문제다.**
급등주 목록을 보고 "발굴을 넓히자"로 가는 것은 사후확신이다.

### 🚨 그런데 그 클래스 평균 자체가 **측정 지평에 따라 부호가 뒤집힌다** (2026-07-31 실측)
이 자리에 원래 *"D n=89 −0.70pp vs B n=26 +1.93pp ⇒ 발굴은 안 새고 보유가 샌다"* 가 박혀 있었고,
그 문장이 `pipeline/README.md` 와 `industry_kr.md` 로 퍼져 **프로토콜 변경의 근거로 인용**됐다.
**같은 07-20 창을 지평만 늘려(07-28~30 폭락 + 07-31 반등 포함) 다시 채점하면 순서가 통째로 뒤집힌다:**

| 클래스 | 07-23 기록(당시) | **오늘 재채점 07-20 창** | **07-24 창** |
|---|---|---|---|
| D.발굴 부재 | −0.70pp (n=89) | **+2.58pp** (n=48) | **+3.57pp** (n=47) |
| C.스쳐감 | — | +2.56pp | +2.35pp |
| A.런에 있었음 | — | −0.31pp | −0.73pp |
| B.커버리지 소실 | **+1.93pp (n=26) 최악** | **−4.68pp (n=51) 최선** | **−4.90pp (n=45)** |

**창을 바꿔도 순서는 같고(D>C>A>B), 지평을 늘리면 뒤집힌다.** ⚠ n 도 안 맞는다(26 vs 51 · 89 vs 48)
— 원 기록이 **재현에 필요한 파라미터를 남기지 않았다**는 뜻이고, 그게 이 결함의 나머지 절반이다.

⇒ **"보유가 샌다"는 상시 주장에서 철회됐다.** 이 스테이지의 클래스 평균은 **그 감사의 관측**이지
데스크의 성질이 아니다. **처방을 쓸 때 클래스 평균을 근거로 삼으려면 (a) 채점 asof 와 floor·top
파라미터를 같이 적고 (b) 최소 두 개의 지평에서 부호가 같은지 확인하라.** 한 창·한 지평의 평균으로
프로토콜을 바꾸면, 다음 폭락 한 번에 그 변경의 근거가 사라진다 — 실제로 그렇게 됐다.

## 이 스테이지가 하는 일

1. **두 원장을 읽는다** — `leak_scan`(전 유니버스 관점) + `reject_ledger score`(명시적 거부 관점).
   전자는 "보지 못한 것", 후자는 "보고 버린 것"이라 겹치지 않는다.
2. **가드 2 적용** — 창의 레짐과 유니버스 평균을 감사문 맨 위에 적는다. 창이 하나뿐이면
   결론에 "단일 창, 부호 미확정"을 명시한다.
3. **클래스별 초과수익으로 누수의 위치를 특정한다** — 이름이 아니라 **클래스**가 판정 단위다.
   개별 급등주는 예시로만 인용한다.
4. **A 클래스는 거부 원장과 조인한다** — 잡았는데 안 걷은 이름은 원장에 사유가 있어야 한다.
   원장에 없으면 그것 자체가 발견이다(**기록되지 않은 거부** = 다음 런이 배울 수 없는 거부).
5. **`revives_if` 가 참이 된 행을 후보로 되돌린다** — 감사의 유일한 *직접* 산출물.
   부활은 자백이 아니라 회수다.
5b. **★ B·C·D 클래스를 `missed_ledger` 행으로 적립한다** — 이 감사가 누적되게 만드는 유일한 장치.
   매핑은 L3 [missed_ledger](../L3_functions/missed_ledger.md) 의 표를 그대로 쓴다
   (B.커버리지소실→`O.커버리지소실` · C.스쳐감→`M.숏리스트탈락` · D.발굴부재→`U.발굴부재` ·
   A.런에있었음→`Q.확신부족`, 단 A 는 거부 원장에 있으면 그쪽이 우선이고 `add` 가 자동으로 막는다).
   ```bash
   python -X utf8 scripts/missed_ledger.py add --date {대상런} --ticker <6자리> --name <종목> \
       --cls <매핑된 클래스> --why "leak_scan <원분류> — <한 줄>" --stage LEAK_AUDIT \
       --enters-if "<진입 조건>" --recheck-date <YYYY-MM-DD>
   ```
   ⚠ **`--top` 상위만 적립하면 결과선택 편향이 들어간다.** 오른 것만 골라 "놓쳤다"고 적으면
   클래스 평균이 구조적으로 양수가 된다(2026-07-31 초기 6건이 정확히 그 표본이고, 스크립트가
   그 경고를 직접 출력한다). **적립은 클래스별 무작위 표본 또는 전량으로 하고, 상위만 담았으면
   감사문에 그렇게 적어라.** 이 원장의 값어치는 **사전등록분**에서 나온다.
6. **처방은 프로토콜 수정으로 쓴다** — "다음엔 잘 보자"는 처방이 아니다.
   어느 L1/L2/L3 의 어느 줄을 무엇으로 바꿀지 적는다. 근거 없는 규칙은 달지 않는다.

## 처방의 형태 (좋은 예 / 나쁜 예)

- ❌ *"SK이터닉스를 놓쳤다. 신재생을 더 봐야 한다."* — 이름 후회, 처방 아님.
- ⚠ *"B 클래스가 최악의 누수(+1.93pp, n=26) → …"* — **한때 이 자리의 모범답안이었고 이제 반례다.**
  같은 창을 긴 지평으로 재채점하니 B 가 −4.68pp(최선)로 뒤집혔다. 처방의 형식은 맞았지만
  **근거의 수명이 짧았다.** 클래스 평균을 처방 근거로 쓰려면 **채점 asof·floor·top 을 함께 적고
  두 지평에서 부호가 같은지 확인**한 뒤에 쓴다.
- ✅ *"D 와 B 의 부호가 지평에 따라 뒤집힌다(07-20 창: 지평 07-23 에서 B +1.93, 지평 07-31 에서 −4.68).
  → 이 스테이지의 EXIT CHECK 에 '두 지평 부호 일치' 를 넣고, 단일 지평 평균으로 프로토콜을 바꾸지 않는다."*
- ✅ *"거부 원장 24건 중 67%가 노이즈. → 거부 사유를 정교하게 쓰는 노동을 줄이고
  BET 후보 폭을 넓힌다(측정된 무의미를 근거로)."*

## ✅ EXIT CHECK
- [ ] `leak_scan --run {대상}` · `reject_ledger score` 둘 다 실행, 산출 인용.
- [ ] **창의 레짐과 유니버스 동일가중 평균이 문서 최상단에 있다.** 벤치로 지수를 쓴 문장 0개.
- [ ] **선행검정 표만 인용했다** — 후행 수익률로 상태를 채점한 문장 0개(가드 1).
- [ ] 네 클래스 전부 **클래스 초과수익**으로 판정했고, D 를 초과수익 확인 없이 실패로 세지 않았다.
- [ ] 🚨 **클래스 평균을 처방 근거로 쓴다면 채점 asof·`--floor-jo`·`--top` 이 함께 적혔고,
      최소 두 지평(예: 대상런 +3세션 · +8세션)에서 부호가 같은지 확인됐다.** 한 지평만 보고
      프로토콜을 바꾸지 않는다 — 그렇게 만든 "보유가 샌다"가 한 주 만에 뒤집혔다(2026-07-31).
- [ ] A 클래스가 거부 원장과 조인됐고, **원장에 없는 거부**가 있으면 그 사실이 발견으로 기록됐다.
- [ ] `revives_if` 참이 된 행이 후보로 되돌아갔거나, 되돌리지 않은 이유가 적혔다.
- [ ] **B·C·D 클래스가 `missed_ledger` 에 적립됐다** — 적립 없이 끝난 감사는 다음 감사가 같은 이름을
      처음부터 다시 발견하게 만든다. 표본이 `--top` 상위뿐이면 **그 편향이 감사문에 명시**돼 있다.
- [ ] 처방이 **파일·줄 단위 프로토콜 수정**으로 쓰였다(이름 후회 아님).
- [ ] 결론이 단일 창에 기대면 그렇게 표시했다(가드 2).
