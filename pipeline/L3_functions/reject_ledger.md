# L3 · reject_ledger — 거부를 적립하고 채점한다

> **Single-role unit.** Independent — no ordering; an L2 calls it when needed. Does ONE thing.

- **Role**: 데스크가 **버린 것을 자산으로 만든다.** 거부(DROP/PASS/강등)를 기계가독 원장에
  적립하고, 사유 클래스별 초과수익을 누적 채점한다. 거부는 진입만큼 자주 하는 행동인데
  지금까지 유일하게 **점수가 남지 않는 행동**이었다 — 이 유닛이 그 자리를 채운다.
- **Input**: 거부 1건 (날짜 · 티커 · 종목명 · 사유클래스 · 근거 한 줄 · 스테이지 · **부활조건** ·
  **재확인일**) 또는 채점/감사 요청.
- **CLI**:
  ```bash
  python -X utf8 scripts/reject_ledger.py add --date 2026-07-22 --ticker 005380 \
      --name 현대차 --cls K.본문반증 --why "이틀째 파업·생산차질 확대" --stage EVENT_ALPHA \
      --revives-if "파업 타결 + 기관 순매수 부호 유지" --recheck-date 2026-07-30
  python -X utf8 scripts/reject_ledger.py score      # 전체 채점 + 클래스/유형 집계
  python -X utf8 scripts/reject_ledger.py due        # ★ 재확인일 도래/경과 + 부활조건 없는 레거시 감사
  python -X utf8 scripts/reject_ledger.py resolve --ticker 475150 --date 2026-07-16 \
      --outcome revived --note "..."                # 원장 원본은 안 건드림(append-only), 해소만 별도 기록
  ```
- **Output**: `out/reject_ledger.jsonl` (적립, append-only) + `out/reject_ledger_resolutions.jsonl`
  (해소 기록, append-only, 원 행과 분리) + 채점표 — 건별 초과수익, **사유클래스별** 평균, **유형별**
  (`measured` / `structural` / `narrative`) 평균, 그리고 `due` 의 감사 목록.

⚠ **`add` 는 `--revives-if` 와 `--recheck-date` 없이는 실행되지 않는다(2026-07-23부로 스크립트가
강제).** 두 인자를 채우지 못했다면 이 유닛을 부를 자격이 아직 없는 것이다 — 근거를 다시 좁혀서
조건과 날짜를 만들 수 있을 때 다시 호출한다. **빈 값으로 우회할 방법은 CLI 에 없다.**

## 사유 클래스는 세 유형으로 접힌다 — 이 접힘이 이 유닛의 요점

| 유형 | 예 | 뜻 |
|---|---|---|
| `measured` | 약한손 · OBV분배 · 차트붕괴 · flow미도착 · 밸류소진 | **관측값**이 거부 근거 |
| `structural` | 상관가드(리스크유닛 중복) · 섹터중립 | **포트폴리오 구조**가 거부 근거 |
| `narrative` | 테마소멸 · 테제반증 · 본문반증 | **이야기**가 거부 근거 |

**벤치는 지수가 아니라 시총 1조+ 동일가중이다.** 지수는 대형주 사건에 지배된다 —
실측 2026-07-23: 동일가중 **−2.6%** vs 시총가중 **−15.7%**, 중앙값 **−1.4%** vs ^KS11 −21.6%.
지수 대비로 재면 거의 모든 거부가 "옳았다"고 나온다(대형주가 빠졌으니까). 그건 측정이 아니다.

## ⚠ 첫 관측 (2026-07-23, KR, 24건, 창 3~12세션) — **누적의 시작이지 결론이 아니다**

- **16/24 = 67% 가 |초과| ≤5pp = 노이즈.** 거부 노동의 3분의 2가 결과를 바꾸지 않았다.
  → 그 노력은 **후보 확장**으로 돌리는 게 이득이다.
- **손해합 +83.8pp vs 이득합 −38.4pp** — 꼬리가 손실 쪽에 있다. 잘 거부해 버는 것보다
  잘못 거부해 잃는 게 크다. **거부는 대칭 행위가 아니다.**
- 유형별: `narrative` **+12.8pp** · `measured` **−0.9pp** · `structural` **−4.5pp**.
  ⚠ **`narrative` 의 +12.8pp 는 전부 한 종목(475150)이다.** 그 종목을 빼면 −1.3pp = 노이즈.
  클래스별 n 이 1~4다. **평균을 규칙으로 박제하지 말고 매 런 재출력하라** — 이 유닛의
  존재 이유는 판정이 아니라 **표본 적립**이다(P4).

## 부활조건(`--revives-if`)이 이 원장의 핵심 필드다

킬은 **테제**에 대해 이뤄지는데 로그는 **종목**에 걸린다. 테제가 바뀌거나 킬을 만든 조건이
되돌아오면 해제될 길이 있어야 한다. 실측 사례: 475150 은 공매도 `covering→building(+0.54)` 로
거부됐고 며칠 뒤 **`building→covering(−0.28)` 로 되돌아왔다** — 조건은 소멸했는데 금지는 남아
있었다. **부활조건이 빈 칸인 거부는 영구 금지이며, 영구 금지는 거의 언제나 과하다.**

## ⚠ 2026-07-23 — 이 규율은 지켜지지 않고 있었다, 그리고 그게 원장의 가장 비싼 두 줄을 냈다

25건 중 **24건이 `revives_if` 를 빈 칸으로 남긴 채 적립됐다.** `score` 는 매 런 돌았지만, 빈 칸은
"조건이 참이 됐는지" 물을 대상 자체가 없어 **아무도 다시 열어보지 않았다** — `carryover.md` §3b가
"조건이 참이 된 행을 찾으라"고 적어 놨어도, 찾을 조건이 없으면 그 지시는 실행 불가능한 문장이었다.
그 결과가 **475150 의 두 차례 거부(+41.2pp, +26.9pp, 원장 전체 손해의 대부분)** — 둘 다 서사
근거(테마소멸·테제반증)였고, 둘 다 사용자가 직접 원장을 다시 열어보라고 요청한 뒤에야 재조사돼
되돌려졌다(`resolve --outcome revived`, 같은 날).

**이 유닛은 더 이상 "조건을 채우면 좋다"는 권고로 남지 않는다 — 다음 세 가지를 코드와 프로토콜이
직접 막는다:**

1. **`add` 는 `--revives-if`·`--recheck-date` 없이 실행될 수 없다.** 사람이 매번 기억해서 채우는
   방식으로는 이 결함이 반복된다는 것이 24/25 라는 숫자로 이미 증명됐다 — 그래서 스크립트 레벨에서
   막는다(우회 불가).
2. **HANDOVER 는 `due` 를 건너뛸 수 없다** (`carryover.md` §3b, `handover.md` EXIT CHECK). `score`
   만 도는 HANDOVER는 이 감사를 하지 않은 것과 같다 — `due` 가 낸 목록 중 어떤 행도 다음 HANDOVER로
   조용히 두 번 넘어가면 안 된다(EXPIRED 시나리오와 같은 취급).
3. **레거시 24건(부활조건 없이 적립된 행)은 한 번에 정리되지 않는다.** 세팅을 되돌려 소급 채우지
   않는다(append-only 원칙 — 과거 판단을 세탁하지 않는다). 대신 `due`가 매 런 감사 목록으로 계속
   올리고, HANDOVER가 그중 하나씩(또는 여럿) `resolve`로 닫아나간다. **감사 목록이 줄지 않는 채로
   여러 런을 넘기는 것 자체가 다음 dig 감이다.**
